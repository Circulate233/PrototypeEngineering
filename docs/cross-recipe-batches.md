# 跨配方控制器的统一批次

`CrossRecipeController` 以同一批处理配方，不再让短配方先完成、腾出并行后继续补入。空载扫描仍走已选择的线程策略；第一轮真正工作捕获时封闭整机所有配方宿主的当前成员，运行期间暂停新扫描/准入，整批完成后才选择下一批。多线程控制器保留各工位独立完成的行为。

## 时间与进度

批次工作时长为 `ceil(Σ(配方原时长 × 有效并行数) / Σ有效并行数)`。向上取整到工作刻，使用整数精确累加，避免乘法溢出或浮点平均把工作时间算短。START 事件最终改变并行数时，在全部 START 成功、首个 TICK 之前重算权重。运行期间不因某个成员取消而重算已确认时间或退还历史 IO。

批内进程使用相同工作时钟。速度按各成员当前有效并行数加权，成功 TICK 才推进共同进度；GUI 进度分母读取批次时长，canonical 配方和持久化配方身份不修改。START、TICK、END 仍经原 coordinator 和资源事务，短配方不会提前 END。任一成员本轮缺料、缺电或输出受阻，同批其他成员的该轮也回滚；整批可继续时再重试。任一 END 拒绝时整批 END 都不发布，避免部分产物提前结算。

例如 2 刻配方 ×1 并行与 4 刻配方 ×2 并行，原工作量为10，统一时长为4刻。最终产物在共同 END 结算；每个成员的 START/TICK/END 事件保留原调用与补偿协议。

## 合批条件与逐刻收支

固定资源的逐 TICK 输入和输出必须同时相同，比较单位并行的实际 AEKey/NBT 和数量，累加相同 key 后比较；输入来源分配、概率和输出溢出语义也参与匹配。每tick 1 mB水只能与同样输入的配方合批；无TICK输入不能与需水配方混入，同样输入但不同TICK输出也不能混入。未匹配的配方仍可在下一批单独工作，不从配方池删除。

确定性逐 TICK IO 保留原配方 `单位逐刻量 × 原时长 × 最终并行数` 的总量，并分摊到新的批次进度。按累计进度边界计算本次整数份额，整数尾差在成员和工作刻间分配；快慢速、阻塞重试、时长取整与存档恢复均不凭重复扣料补差。有限long范围之外的单次费用在预留前明确失败，不静默截断。`AEKey2LongMap` 用于数量聚合。

FE 的 START输入、原逐TICK输入/输出和 END输出分别归入输入/输出总额，普通根需求在统一工作时段分摊，沿原能源来源分配/容量/事务预留付款。原时长0且整批也为0时保留 START/END 原规则，不虚构TICK。PN数值工作量按相同批次份额缩放，机器lease、权限/owner及预算来源检查不变。

概率IO、检查点、选择器和不透明外部系统不能只用平铺key数量证明执行次数相同：默认保守要求匹配相同策略/结构及原时长，保持这些既有业务的执行时间语义。外部 `RecipeRequirementSystem.crossRecipeTickIo(payload)` 提供稳定的逐TICK收支等价key，默认按payload区分；明确无TICK收支的系统返回null。只有确实按当前批次时间分摊自己事务的实现才能将 `crossRecipeRetimesTickIo(payload)` 声明true。PN系统使用完整数值资源向量作为key并实际按份额计量。每轮在实际事务前复核有效overlay，START后把原本相同的收支改成不同会拒绝执行，不能混算。

## 保存与验证

`RecipeProcessNbt` 的可选 `CrossBatch` 保存准确批次UUID、统一时长、冻结并行及材料/FE尾差位置；不改变canonical recipe/revision/graph检查，也不持久化存储许可、来源、预留或执行线程。能耗路径要求与实际冻结需求图完整对应，缺失/重复/未知路径拒绝；整组工位恢复先验证同批身份和时长，再替换旧成员。旧无批次字段的新进程可在首次工作时建批。

既有测试文件中新增三项真实行为回归：固定输入/输出不兼容拒绝、非整数加权时长、精确FE/材料总量、途中恢复及阻塞END；START改并行与不同速度的共同进度；实际scheduler多个宿主只推进一次、阻塞TICK的共同补偿。未添加镜像公式/源码文本测试。完整构建及本机IDE检查证据见[实施进度](implementation-status.md)，实际游戏由用户自行启动复验。
